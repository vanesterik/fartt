# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Fartt (Financial Analysis Real Time Trading) is an MCP server that gives an agent the tools to analyse stocks on Euronext and US exchanges, with Claude Code as the analyst and the operator's interface. It's decision support for personal use: the agent combines many signals (market data, technical indicators, support/resistance, fundamentals, market context, charts) into a view, and a journal scores every call afterwards against a world index ETF. The server owns data, risk limits and state; the agent can read the limits but never change them. It's a solo research project, not production infra.

The plan is the PRD, `docs/product/stock-analysis-prd.md` (problem, users including the agent, the eight-step analysis procedure, tool surface, the three stages from paper trading to server-placed orders and their gates, the risk config, risks and open questions). It's delivered in epics on the board, in this order: **A** Data Foundation (#88), **B** Technical Analysis (#89), **C** Journal & Evaluation (#90), **D** Analysis Pipeline (#91; A–D are the walking skeleton, a full analysis on one ticker), then **H** Trade Plan & Risk (#95; paper trading starts), **F** Market Context (#93), **G** Fundamentals & Screening (#94), **K** News (#133), **E** Visualization (#92), **I** Validation (#96), **L** Saxo Market Data (#140; switched on when stage 2 starts), **J** Live Orders (#101). The letters are the order the epics were planned in; this is the order they're built in (decided at the walking-skeleton milestone). Stories are written just in time, one epic at a time. A story's design and implementation plan live in its issue, in the latest `role:design` comment (see Team workflow below). `docs/specs/` and `docs/plans/` hold the designs and plans of epics A and B, written before this workflow; they're history, and new ones aren't added there.

The project follows the [cookiecutter data science](https://drivendata.github.io/cookiecutter-data-science/) layout: `docs/` for the PRD (and the early designs and plans), `src/fartt` for library code, `tests/` for unit tests and `tests/integration/` for the integration tests.

## Current state of the codebase (important)

**What exists and works** (epic A, stories A1–A4; epic B, stories B1–B3; epic C, the journal, scoring and get_performance; epic D, the `analyze_ticker` prompt and the analysis session's permission profile; together the walking skeleton; and from epic H, the risk config):

- **Stock data provider.** `fartt/data/` holds the `DataProvider` Protocol (`listing`, `history(ticker, start)`, `quote`) and `YFinanceProvider`, the only module that imports yfinance. Prices are split-adjusted, not dividend-adjusted; dividends and splits come out as separate records.
- **Stock cache.** `fartt/stock_cache.py` keeps each ticker's daily candles, dividends, splits and listing under `assets/stocks/<TICKER>/` and brings them up to date on demand.
- **The MCP server.** Claude Code starts it from `.mcp.json` (`uv run fartt`). It has twelve tools: ten read tools, `plan_trade(ticker, entry, stop, target, valid_for)`, which sizes a long trade against the risk limits after costs, `get_risk_config()`, which returns the operator's risk limits and trading costs, `get_analysis_procedure(ticker)`, which returns the analysis procedure for a ticker, `get_candles(ticker, count)`, `get_quote(ticker)`, `get_indicators(ticker)`, `get_trend(ticker)`, `get_support_resistance(ticker)` and `get_decisions(status, ticker, limit)`, which reads the journal back, and `get_performance()`, which reports how the scored calls did, `record_decision(...)`, which writes a call to the journal (a buy with its trade plan), and `score_decisions()`, which scores the calls whose horizon has passed. It has one prompt, `analyze_ticker(ticker)`, which the operator invokes in Claude Code as `/mcp__fartt__analyze_ticker ASML.AS`: the PRD's eight-step analysis procedure for that ticker, ending in a recorded call. The server's instructions tell the agent to call `get_analysis_procedure` before analysing a ticker, so an analysis asked for in plain words follows the same procedure.
- **Analysis procedure.** `fartt/procedure.py` holds the eight steps as data, with the tools that carry each step today or the epic that adds them, and generates the text of the `analyze_ticker` prompt and the `get_analysis_procedure` tool from them.
- **Analysis session.** `task analyse` starts Claude Code with only the `fartt` server's tools, under a checked-in permission profile (see Running an analysis below); a plain `claude` stays the development session.
- **Technical analysis.** `fartt/technical/indicators.py` computes moving averages, RSI, MACD, ATR and volume with their states over plain candles, `trend.py` the daily and weekly trend, and `levels.py` the support and resistance zones with the signs that the nearest support holds or breaks.
- **Journal.** `fartt/journal.py` keeps every call the agent records (buy or pass, horizon, reasoning, signals, and the stock's and IWDA.AS's last closes) in `assets/journal/decisions.jsonl`, append-only, and `get_decisions` reads them back. `score_decisions` scores each call whose horizon has passed against IWDA.AS, in EUR (`fartt/scoring.py`), and stores the score as a line of the same file; `get_performance` reports the hit rate and average returns over the scores (`fartt/performance.py`). Unlike `stocks/`, it can't be rebuilt.
- **Risk config.** `assets/risk.toml`, checked in, holds every risk limit (PRD section 6) and the trading costs per exchange (Saxo's Dutch Bronze tariff of 13 July 2026, with the French, Italian and Irish taxes and the Irish levy). `fartt/risk_config.py` checks it when the server starts, and `get_risk_config` returns it; `plan_trade` and a recorded buy's plan are held to it.
- **Helpers later epics build on**, not called by the server yet: the DataFrame indicators behind the chart, a candlestick chart (epic E) and a long-only backtest (`calculate_trade_returns`, epic I).

**What doesn't exist yet:** the rest of epic H (paper orders and positions, the portfolio's value, the open-position limit and kill switch, and step 6 of the procedure, which doesn't name `plan_trade` yet) and epics E–L: the tools for steps 1–4 and 6 of the procedure (they're reported as skipped), market context, fundamentals and screening, news, charts, validation, Saxo market data and live orders.

`uv run pytest` collects and passes cleanly; don't assume the suite is broken.

## Commands

The everyday commands are tasks in `Taskfile.yml`; `task --list` names them. `task setup` installs the project from `uv.lock` and wires up the git hooks, and `task check` (lint + typecheck + test) is the same command the pre-push hook runs, so the two cannot drift apart. `task` comes from the global `mise` setup (`mise use -g aqua:go-task/task`); it cannot install itself, so it is the one prerequisite `task setup` does not cover.

```bash
task setup                       # uv sync + install the lefthook hooks
task check                       # lint + typecheck + test, as the pre-push gate runs them
task lint                        # ruff format --check + ruff check, without writing
task format                      # ruff format + ruff check --fix
task typecheck                   # pyright (strict mode, src/ only — tests/ excluded)
task test                        # pytest, offline
task test:integration            # the stdio tests, offline on the data snapshot, in parallel (deselected by default)
task test:network                # the tests that call Yahoo, in parallel (deselected by default)
task test:snapshot               # rebuild the integration tests' data snapshot from Yahoo
task pre-commit                  # the pre-commit hook's checks over staged files
task outdated                    # direct dependencies with a newer release
task analyse                     # Claude Code limited to the fartt server's tools, for an analysis (alias analyze)
```

Tool versions are upgraded on purpose, never because a run nags: ruff's rule set is pinned in `pyproject.toml`, and pyright's new-release warning is silenced. Instead, Dependabot (`.github/dependabot.yml`) opens weekly pull requests for newer releases: minor and patch updates grouped into one for dev tools and one for runtime dependencies, each major update on its own. There's no CI, so check a Dependabot pull request out and run `task check` (or push to it) before merging. A runtime update also needs `task test:integration` and `task test:network`: the unit tests run on a fake provider, so an MCP SDK or exchange_calendars release that breaks the stdio server passes `task check` unnoticed, and a yfinance release that breaks the live fetch passes everything but `test:network`. `task outdated` is the on-demand version.

Everything below remains the direct route, and is what the Taskfile calls. Dependency management is via `uv` (see `uv.lock`), run from the repository root. The Python version is pinned in `.python-version` (3.14) and matched by `requires-python` in `pyproject.toml`; Dependabot doesn't track it, so moving to a new Python release is a deliberate change to both.

```bash
uv sync                          # install dependencies
uv run fartt                     # run the MCP server over stdio (Claude Code does this from .mcp.json)
uv run pytest                    # run test suite
uv run pytest tests/test_server.py::test_count_beyond_the_history_returns_what_is_cached  # single test
uv run pytest -m "integration and not network" -n auto  # the offline integration tests
uv run pytest -m network -n auto # run the live tests, in parallel (deselected by default)
uv run ruff format .             # format
uv run ruff check . --fix        # lint
uv run pyright                   # type check (strict mode, src/ only — tests/ excluded)
```

There is no CLI: the agent calls the server's tools, and a ticker's cache fills on its first call. The server reads `FARTT_ASSETS_DIR` for the cache's folder from the environment or else the repository's `.env` (copy `.env.example`), defaulting to `assets/` in the repository wherever it was started from; a relative path is relative to the repository. The assets folder holds `stocks/`, a cache that's safe to delete, `journal/`, the record of every call, which can't be rebuilt: never delete it, and `risk.toml`, the risk limits and trading costs, the one file in it git tracks (`.gitignore` ignores `assets/stocks/` and `assets/journal/` only). The server reads `risk.toml` once at start and refuses to start, naming the file and every problem, when it's missing, unreadable or holds a value it can't accept; an assets folder elsewhere needs its own copy. Changing a limit or a cost is a deliberate commit to that file, followed by a restart, as changing the analysis profile is; no tool changes it, and the analysis session has no file tools. `FARTT_NOW` (environment only, never `.env`; ISO 8601 with an offset) pins the server's clock to one moment, so a cache filled up to it counts as current and nothing is fetched for it: the integration tests run the server on a checked-in snapshot this way. An unreadable value stops the server saying why. It logs to stderr only, since stdout carries the protocol.

The integration tests (`tests/integration/`, all marked `integration` by its `conftest.py`) start the server from `.mcp.json`'s command with `FARTT_ASSETS_DIR` set to a temporary folder. Most run on a copy of the checked-in snapshot (`tests/integration/snapshot/`, the `seeded_assets` fixture) with the server's clock pinned to the snapshot's moment and Yahoo out of reach (`snapshot.OFFLINE`), so they're offline and give the same result every run; `snapshot.py` names the tickers and the moment, and `task test:snapshot` rebuilds it. The few that are about Yahoo itself (a first download, a quote, a ticker Yahoo doesn't list) are also marked `network`; refilling a cut snapshot from Yahoo keeps the clock pinned (`snapshot.PINNED`). A new test is offline unless it needs Yahoo's answer. `tests/integration/test_server_stdio.py` checks the whole server: `test_tools_over_stdio` fills an empty folder from Yahoo and calls every tool (`network`), and the stdout check asserts, offline, that stdout carries only JSON-RPC, including anything written at shutdown. Each new tool joins it: the test role adds its name to `EXPECTED_TOOLS` and its call to `test_tools_over_stdio` (integration tests are the test role's, not the builder's).

Hooks are managed by `lefthook` (`.lefthook.yml`) and stand in for CI, which this project doesn't have. On every commit, staged Python files get `ruff format` + `ruff check --fix`, then `pyright` and `pytest` run. On every push, `task check` runs the full suite on the whole repository (`ruff format --check .`, `ruff check .`, `pyright`, `pytest`), because pre-commit only sees staged files and a commit touching only `pyproject.toml`, `uv.lock` or `.mcp.json` would otherwise skip tests and type checks. `git push --no-verify` skips the gate for one push; use it deliberately, never by default. Tests marked `integration` or `network` are deselected by default; run them with `task test:integration` (offline) and `task test:network` (Yahoo).

## Running an analysis

An analysis runs in its own Claude Code session, started from the repository with `task analyse` (alias `analyze`); then `/mcp__fartt__analyze_ticker ASML.AS` runs the procedure for a ticker. Asking in plain words ("analyse ASML.AS") works too: the server's instructions send the agent to `get_analysis_procedure` first, which returns the same text; the slash command is the shortcut. Extra arguments go through to `claude`: `task analyse -- --resume`. A plain `claude` in the repository is the development session, with the permissions it always had.

What the session may do: call every tool of the `fartt` server (also the ones later epics add), without a permission prompt, and use its prompt. What it may not do: anything else. There is no shell, no file read, write or edit, no web search or fetch, no subagents or skills, and no other MCP server or connector (Google Drive, Calendar and the like): those tools aren't offered to the model at all, so it can't even propose them. Should one ever slip in, it asks instead of running, also when the user settings set `defaultMode` to `auto`. Anything the analysis changes, it changes through the server (the journal); the risk limits it can only read.

The profile is two pieces, both checked in:

- `.claude/analysis-settings.json`: the permissions, `allow: ["mcp__fartt"]` in `defaultMode: default`.
- The `analyse` task in `Taskfile.yml`: `--restricted` (ignore the user, project and local settings files), `--tools ""` (no built-in tools), `--strict-mcp-config --mcp-config .mcp.json` (only the `fartt` server), `--settings .claude/analysis-settings.json` and `--permission-mode default`.

Changing the profile is a deliberate commit to those two files, as changing the risk limits in `assets/risk.toml` is; an analysis session can't change it, since it has no file tools. Claude Code's flags change between releases, so after a Claude Code update check the profile headlessly: anything that would prompt is denied, and the stream's `init` message lists the tools the session has (only `mcp__fartt__*`) and its `permissionMode` (`default`):

```bash
claude -p --permission-prompts none --output-format stream-json --verbose \
  --restricted --tools "" --strict-mcp-config --mcp-config .mcp.json \
  --settings .claude/analysis-settings.json --permission-mode default \
  "Call get_quote for ASML.AS." < /dev/null
```

## Architecture

- **`fartt/data/`** — the provider layer. `DataProvider` takes tickers in Yahoo's format (`AAPL`, `ASML.AS`); its `NamedTuple` types are `Candle` (with a session `date`), `Dividend`, `Split`, `History`, `Listing` (with `first_trade`, the exchange-local date of Yahoo's `firstTradeDateMilliseconds`, or `None`) and `Quote`, and its errors `UnknownTicker`, `ProviderUnavailable` and `UnsupportedExchange`. `sessions.py` normalises tickers (`normalise_ticker`: stripped, upper-cased, letters, digits, `.` and `-` only, plus an `=X` ending for an exchange rate, so no ticker escapes a cache folder and a future such as `GC=F` isn't taken for an NYSE stock), maps the suffix to an `exchange_calendars` code (`calendar_for`; no suffix is XNYS, then `.AS` XAMS, `.PA` XPAR, `.BR` XBRU, `.LS` XLIS, `.MI` XMIL, `.IR` XDUB, `.OL` XOSL; an exchange rate in Yahoo's format, `EURUSD=X` (`FX_SUFFIX`), is on `FX_CALENDAR` `24/5`, which closes each day at midnight UTC, and `fx_pair(currency)` names the pair that converts a currency to euros (`None` for EUR); anything else is `UnsupportedExchange`; exchange rates aren't in `SUFFIX_CALENDARS`, so no call can be recorded on one), and answers `newest_closed_session` (a 30-minute `CLOSE_MARGIN` after the close), `missing_sessions`, `last_session_of_week` (the exchange's last scheduled session of an ISO week, or `None` outside the calendar's range), `session_after` (the `count`-th session after a day, skipping weekends and holidays), `session_on_or_before`, `exchange_date` and `market_status` (open now, or when the next session opens). `YFinanceProvider(ticker_factory, clock)` returns closed sessions only, maps yfinance's missing-ticker errors and Yahoo's HTTP 404 to `UnknownTicker` and everything else to `ProviderUnavailable`, and turns a bid/ask of 0 into `None`. It sets `yfinance.config.debug.hide_exceptions = False` (the per-call `raise_errors` is deprecated). yfinance, exchange_calendars and mplfinance have minimal stubs under `typings/`.
- **`fartt/stock_cache.py`** — `StockCache(provider, assets_dir, clock)`: each ticker's split-adjusted daily candles (`candles.csv`), dividends and splits (`events.csv`) and listing (`listing.json`) under `assets_dir/stocks/<TICKER>/`. `update(ticker) -> UpdateResult(new_candles, rebuilt, fetched)`: a first update fetches the full history; later ones re-fetch from the last cached session and append what's newer; a split after it, or any change to the last cached candle's prices (volume aside), rebuilds the whole history (files swapped in with `os.replace`, candles last); a cache already holding the newest closed session doesn't call the provider. A ticker without a folder is fetched before its folder is created, so an unknown ticker or an unreachable provider leaves none behind; a fill without cached candles that gets no candles raises `NoHistory(listing)` and writes nothing (an existing folder is never removed). A torn last line is healed first. Reads (`latest`, `events`, `listing`) take a shared `fcntl` lock on the directory's `.lock`, updates an exclusive one.
- **`fartt/server/`** — `build_server(cache, journal, risk_config)` returns the MCP SDK v2 `MCPServer` (the cache also supplies the provider for quotes and the clock for market hours and for the time a call is recorded), and `main()` (the `fartt` console script) builds it on `StockCache(YFinanceProvider(), assets_dir)`, `Journal(assets_dir / "journal")` and `load_risk_config(assets_dir / "risk.toml")` and runs it over stdio; a `RiskConfigError` becomes a `SystemExit` with its message, before anything is served. `get_candles(ticker, count=60)` (`count` 1–200: 200 rows stay well under Claude Code's MCP output limit of about 25k tokens) updates the ticker's cache and returns structured output: `ticker`, `name`, `currency`, `exchange`, `columns`, `rows` as `[date, open, high, low, close, volume]` arrays oldest first (rounded to 4 decimals, as `get_indicators` is; an exchange rate's prices to 6, `scoring.RATE_DECIMALS`, so they're the rates a score uses), `new_candles`, `rebuilt`, `gaps` (sessions missing between the rows), `is_current` and `warning`. An unreachable provider degrades to the cached rows with `is_current: false` and a warning saying how many sessions behind they are, or a `ToolError` when nothing is cached. A listed ticker without a closed session (`NoHistory`) is a `ToolError` worded by `_no_history_error` from the listing's `first_trade` against the newest closed session: on or before it, it can't be analysed and retrying won't help; after it, try again once the first session closes; unknown, both. An unknown ticker, an exchange outside the universe or a cache folder it can't write are `ToolError`s saying what to do; the SDK would otherwise report any other exception as a bare "Error executing tool". `get_quote(ticker)` updates the cache too, then returns `ticker`, `currency`, `last`, `bid`, `ask`, `spread` (a fraction of the midpoint, to 6 decimals; the other floats to 4), `volume`, `average_volume_20d` (the 20 cached sessions before the quote's session, so today never averages with itself), `volume_ratio` (not normalised for time of day), `market_open` and `next_open` (from the exchange calendar), `quote_time`, `delay_minutes` and `note`. A missing or crossed bid/ask makes `bid`, `ask` and `spread` all null, never a zero or negative spread. An unreachable provider is a `ToolError`: a cached quote would be stale by definition. `get_indicators(ticker)` reads the whole cached history and returns `ticker`, `currency`, `based_on` (the session its values are as of), `close`, `sma_20`, `sma_50`, `sma_200`, `ema_20`, `rsi`, `macd`, `atr`, `volume`, `note` (which indicators are null for too short a history), `is_current` and `warning`. `get_trend(ticker)` reads the whole cached history too and returns `ticker`, `currency`, `daily` and `weekly` (each `direction`, `basis`, `based_on`, `close`, `sma_50`, `sma_200` and `last_cross`; `weekly` is null before any week has closed), `aligned`, `note`, `is_current` and `warning`. `get_support_resistance(ticker)` reads the whole cached history and the dividend dates and returns `ticker`, `currency`, `based_on`, `last`, `atr`, `support` and `resistance` (each zone `low`, `high`, `sources`, `touches`, `turns`, `last_touch`, `volume_share`, `strength`, `distance` and `distance_atr`, nearest first), `signs` (`{sign, points, detail}` for the first support zone), `note`, `is_current` and `warning`, within 3,500 characters of JSON. `record_decision(ticker, direction, horizon, reasoning, signals)` records a call: `direction` `buy` (the stock will beat the benchmark, IWDA.AS, over the horizon) or `pass` (it won't), `horizon` 5–60 sessions of the stock's exchange, `reasoning` 1–2,000 characters after stripping, and `signals` at least one `{name, stance, note?}` (`name` from `journal.SIGNALS`, each at most once; `stance` `for` or `against`; `note` up to 200 characters). It refuses (`ToolError`, nothing recorded) unless the stock's and the benchmark's caches hold their exchange's newest closed session, so a call is never stamped with a stale close. It returns the entry as stored: `id`, `recorded_at` (the cache's clock, UTC, whole seconds), `ticker`, `currency`, `exchange`, `direction`, `horizon`, `reasoning`, `signals`, `decision_session` and `close` (the stock's last closed session), `horizon_ends` (`session_after` on the stock's exchange) and `benchmark` (`ticker`, `currency`, `session`, `close`; its session can differ from the stock's) and `plan`. An optional `plan` argument (`PlanRequest`: `entry`, `stop`, `target`, `valid_for`) goes with a `buy` only (a `pass` with one is refused before anything is read): the server works it out again with `_plan_on` on the same read of the stock's whole history the call is stamped from (so call and plan are one session), after the closes are checked, and stores the full `TradePlan` in the entry; a plan that breaks a check or limit records nothing, with `plan_trade`'s words. Without one, `plan` is null. `plan_trade(ticker, entry, stop, target, valid_for=5)` (read-only, open-world; it records nothing) plans with `_trade_plan`: it refuses an exchange rate, brings the ticker up to date with `_snapshot` and refuses it unless it holds the newest closed session (as `record_decision` words it), then hands the snapshot to `_plan_on`, which `record_decision` uses too, so the two refuse in the same words: it takes the ATR from `calculate_indicators` and, for a stock not in EUR, the `fx_pair`'s newest cached close (after an update; it need not be the newest session) to 6 decimals, and returns `trade_plan.calculate_plan` on `_portfolio_value(risk_config)` (the starting capital until the paper portfolio, #145); a `PlanRefused` becomes a `ToolError` ending "Nothing was recorded.". The output: `ticker`, `currency`, `exchange`, `based_on`, `last_close`, `atr`, `entry`, `stop`, `target`, `valid_for`, `rate` (null for EUR), `rate_session` (the session of that close, null for EUR), `warning` (set when the rate is from a session before `based_on`: its session hasn't closed yet, rates closing at midnight UTC, or the provider couldn't update it; the plan is still made), `shares`, `position_value`, `portfolio_value`, `position_share`, `risk`, `risk_share`, `reward`, `reward_to_risk`, `reward_to_risk_before_costs`, `sized_by`, `costs` (`buy`, `sell_at_stop`, `sell_at_target`, each `commission`, `slippage`, `conversion`, `tax`, `fee`, `total`), `limits` and `tariff` (`name`, `currency_conversion`, `slippage_per_leg` and the stock's exchange's costs as `exchange`). `get_decisions(status=None, ticker=None, limit=None, id=None)` reads the journal back without calling the provider or writing anything; `id` returns that one call with its full stored plan (an unknown id is an empty list, `total` 0 and a note), and together with `status`, `ticker` or `limit` is a `ToolError`; otherwise it lists: `status` `open` (not scored yet, including calls whose horizon has passed), `scored` or `all` (the default), and `ticker` normalised as the other tools do (a valid ticker with no calls matches nothing; one that can't be a ticker is a `ToolError`); the two combine. It returns `decisions` newest first (by `id`), each the stored entry plus `status` (`scored` once the journal holds the call's score, else `open`; `_status` is the one place that decides it), `horizon_passed` (`_horizon_passed`: `newest_closed_session` on the stock's exchange, by the cache's clock, has reached `horizon_ends`: due for scoring), `score` (null while open) and `plan` in summary (`trade_plan.PlanSummary`: `entry`, `stop`, `target`, `valid_for`, `shares`, `position_value`, `risk`, `reward_to_risk`, `sized_by`, `based_on`; null without a plan), at most `limit` (1–10, default `MAX_DECISIONS`; ten of the largest entries, each with a plan, are about 51,000 characters, under `MAX_DECISIONS_CHARS`, 60,000), with `total` (how many matched before the cap) and a `note` when the list is empty (naming the filters) or cut short (how to narrow it). A damaged or unreadable journal is a `ToolError` naming the file, for the operator to fix. `score_decisions()` (no arguments; idempotent) reads the journal, splits the open calls into due (`_horizon_passed`) and running, brings each ticker the due calls need (the stock, IWDA.AS and the stock's `fx_pair`) up to date and reads its candles and dividends once per run, scores each due call with `score_call` and stores it with `append_score`. It returns `scored` (`{id, ticker, direction, decision_session, horizon_ends, return, benchmark_return, excess_return, right}`, oldest first), `not_scored` (`{id, ticker, horizon_ends, reason}`: a close or rate not available yet, with "(the provider is unreachable)" when the update of the ticker the reason names failed, or "Yahoo no longer lists X"), each capped at `MAX_SCORED` (50) with a `note` saying how many more, `running`, `already_scored` (including a call another run scored in the meantime) and a `note` when no open call is due. A call that can't be scored stays open for a later run; a damaged journal is a `ToolError`, as in `get_decisions`. `get_performance()` (no arguments) reads the journal without calling the provider or writing anything and returns `basis` (calls, not trades: EUR against IWDA.AS, no costs or position sizes), `min_calls` (`performance.MIN_CALLS`, 10), `scored`, `open` and `due` (open calls whose horizon has passed, by `_horizon_passed`; left out of every figure), `overall`, `buy` and `pass` (each `calls`, `hit_rate`, `average_return`, `average_benchmark_return`, `average_excess_return`, `average_edge`, `period` and `note`), `signals` (all eight of `journal.SIGNALS`, each `used` and `not_used`: `calls`, `hit_rate`, `average_excess_return`, `average_edge`, `note`), `tickers` (each ticker with a scored call: `calls`, `open`, `hit_rate`, `average_excess_return`, `average_edge`, always filled; most scored first, at most `MAX_TICKERS`, 50) and a `note` (nothing scored yet, calls due for `score_decisions`, tickers left out). A group below the minimum keeps its count and period with its figures null and a note; a damaged journal is a `ToolError`, as in `get_decisions`. `record_decision` and `plan_trade` refuse an exchange rate (`EURUSD=X`); the read tools accept one. The cache update, read and staleness check all candle-based tools share are in `_snapshot`. The prompt `analyze_ticker(ticker)` (one required argument) checks the ticker offline (`_analysable_ticker`: `normalise_ticker`, `calendar_for`, and an exchange rate refused, as `record_decision` refuses one, raising `NotAnalysable` with a message ending in `TICKER_FORMAT`) and returns one user message, `procedure.analysis_prompt` for the normalised ticker; `_prompt_ticker` turns a refusal into an `MCPError` with `INVALID_PARAMS` (an `MCPError` passes through the SDK's prompt rendering; anything else becomes a bare "Error rendering prompt"). `get_analysis_procedure(ticker)` (read-only, closed-world) is the same text as a tool, for the agent, which can't load a prompt itself: it returns `ticker` (normalised) and `procedure` (`analysis_prompt`, identical to the prompt's message), and refuses what the prompt refuses, with the same message, as a `ToolError`. Neither calls the provider or writes anything; whether the ticker is listed is left to the tools the procedure names. `get_risk_config()` (no arguments; read-only, closed-world) returns the config as read at start, unrounded, without calling the provider or writing anything: `source` (the file's absolute path), `limits` (`starting_capital`, `max_risk_per_position`, `max_position_size`, `max_open_positions`, `min_reward_to_risk`, `kill_switch_drawdown`) and `costs` (`tariff`, `currency_conversion`, `slippage_per_leg` and `exchanges`, per calendar code in `SUFFIX_CALENDARS` order: `commission`, `commission_min`, `commission_max` (null for none), `commission_currency`, `tax_on_buy`, `fee_on_sell`, `fee_per_trade` and `suffixes`, the ticker suffixes on that calendar, `""` for none). `INSTRUCTIONS` tells the agent to call `get_analysis_procedure` before analysing a ticker, unless the prompt already gave it the procedure, and that the risk limits and costs are the operator's, readable with `get_risk_config` and never changeable by the agent, and that `plan_trade` sizes a buy and `record_decision` takes the plan.
- **`fartt/risk_config.py`** — `load_risk_config(path) -> RiskConfig(source, limits, costs)`: reads `risk.toml` (`RISK_FILE`) with `tomllib` into strict pydantic models with `extra="forbid"` (`RiskFile`, the file's schema; `Limits`, `Costs`, `ExchangeCosts`), with no defaults in the code. It raises `RiskConfigError(path, problems)`, listing every problem as `<dotted key> = <value>: <what's wrong>`, for a missing file (copy the repository's), an unreadable one, invalid TOML (with its line and column), a missing or unknown key, a wrong type (strict: no bool for a number, no 8.0 for a count), a value out of range (`starting_capital` > 0; `max_risk_per_position` in (0, 1) and not above `max_position_size`, in (0, 1]; `max_open_positions` ≥ 1; `min_reward_to_risk` ≥ 1; `kill_switch_drawdown` in (0, 1); every rate in [0, `MAX_RATE`), 0.05, a typo guard; `commission_min` and `fee_per_trade` ≥ 0; `commission_max` above `commission_min`; `commission_currency` three capitals), and `costs.exchanges` without exactly one table per `SUFFIX_CALENDARS` code. The checks across keys run on the raw TOML, so one run lists every problem.
- **`fartt/journal.py`** — `Journal(directory)`: `decisions.jsonl` (UTF-8 JSON Lines, every line ending in a newline) and its `.lock`, the directory created on the first write. `append(draft) -> Decision` takes an exclusive `fcntl` lock, cuts a torn last line, gives the entry the next `id` (1, 2, 3, ...) and writes it as one line with `"kind": "decision"`, then `fsync`s; `decisions()` reads every decision line under a shared lock, oldest first. `append_score(score) -> Score | None` writes a call's score as a `"kind": "score"` line under the same lock, once: `None` (nothing written) when the call already has one, a `ValueError` when there's no such call; `scores()` returns them keyed by `decision_id`. A score line before its call's line, or a second one for a call, is a damaged line. No complete line is ever rewritten or removed; a damaged one is a `ValueError` naming its line, for the operator to fix. A decision line's `plan` holds a buy's `TradePlan`, or null (also when absent, in lines from before plans). `kind` lets later stories add other line kinds to the same file. `Signal`, `BenchmarkClose`, `DecisionDraft`, `Decision`, `Leg`, `BenchmarkScore` and `Score` (its `return_` field is `return` in JSON) are the pydantic models; `BENCHMARK = "IWDA.AS"` and `SIGNALS` (the eight signal names) live here too.
- **`fartt/trade_plan.py`** — a long trade plan as pure functions over the risk config's models. `leg_costs(value, rate, currency, exchange, costs, side) -> LegCosts` prices one trade in EUR at `rate` (units of the stock's currency per euro, `None` for EUR): `commission` (`min(max(value × commission, commission_min), commission_max)`, in `commission_currency`, the stock's currency or EUR; any other is `PlanRefused`), `slippage`, `conversion` (not for EUR), `tax` (`tax_on_buy` on a buy, `fee_on_sell` on a sale), `fee` (`fee_per_trade`, in `commission_currency`) and `total`, each rounded to the cent. `calculate_plan(...) -> TradePlan` checks the prices (each above 0, `valid_for` 1–`MAX_VALID_FOR` (10), stop < entry < target, an ATR known, entry at most `MAX_ENTRY_ATRS` (1) ATR above the last close), then sizes: the largest whole number of shares whose value (`shares × entry / rate`) is within `max_position_size` of the portfolio and whose risk (the loss at the stop plus the buy leg and the sale at the stop) is within `max_risk_per_position`, both compared to the cent; `sized_by` is `max_position_size` when that limit binds (also on a tie). It refuses 0 shares (naming each limit one share breaks, with what it would risk or cost) and a reward-to-risk after costs (reward: the gain at the target less the buy leg and the sale at the target) below `min_reward_to_risk` (naming the value and the shortfall), each with `PlanRefused`. EUR amounts are to the cent, shares of the portfolio and reward-to-risk to 4 decimals, prices as given.
- **`fartt/scoring.py`** — `score_call(decision, candles, dividends, benchmark, rates, scored_at) -> Score`, a pure function over cached data. Every return is in EUR: a price is divided by the `EUR<CCY>=X` close of its session (`rates`, `None` for a EUR stock; when Yahoo has no rate on the day, the latest within `RATE_LOOKBACK_DAYS` (5) before it, once the rate's candles reach the day). The stock's return runs from `decision_session` to `horizon_ends` on the cached split-adjusted closes (not the decision's stored close), with dividends going ex after the first and up to and including the second added gross, converted at the end's rate; the benchmark's runs from its stamped session to its last XAMS session on or before `horizon_ends`. `excess_return` is the difference; a `buy` is right above 0, a `pass` at 0 or below. Closes and dividends are rounded to 4 decimals, rates and returns to 6, and returns are computed from the rounded values. A missing close or rate raises `Unscorable`, whose message is the reason and whose `ticker` is the stock, benchmark or rate it names.
- **`fartt/procedure.py`** — the PRD's analysis procedure as data: `STEPS` (eight `Step(number, name, purpose, tools, epic, detail)`; a step without tools names the epic that adds them and is reported as skipped), `EARLIER_CALLS_TOOL` (`get_decisions`, before step 1), `TOOL_SIGNALS` (the `journal.SIGNALS` names each tool's output feeds), `HORIZON` (20 sessions, fixed until epic H), `REPORT_SECTIONS` and `procedure_tools()` (every tool it names; a unit test checks each is registered). `analysis_prompt(ticker)` generates the prompt text from them plus the fixed decision rules (evidence first; no `buy` while the weekly trend is `down`; weighed, not summed; when in doubt `pass`, and which kind; no call on an open call or stale data). A later epic fills in its step by adding its tools to the entry and clearing `epic`.
- **`fartt/performance.py`** — `calculate_performance(decisions, scores) -> Performance`, pure functions over the journal's models: the groups (`Group`), signals (`SignalPerformance`, a signal used with either stance) and tickers (`TickerPerformance`) `get_performance` returns. Every figure comes from the stored scores: `hit_rate` is the share `right` (4 decimals), each average the mean of the stored values (6 decimals), and `edge` a call's excess return for a `buy` and its negation for a `pass`, so it reads right in groups that mix directions. Groups and signal sides report figures from `MIN_CALLS` (10) scored calls; tickers always do.
- **`fartt/technical/`** — the technical analysis as pure functions over `list[Candle]` (oldest first), no I/O: `indicators.py::calculate_indicators(candles, ex_dividend)` returns pydantic blocks the server returns as they are. Each value comes with its state (above/below, rising/falling/flat, the RSI zone and how many sessions it's held, the last MACD cross, ATR stretch from the SMA 20, volume ratios with ex-dividend sessions left out of the down-day ratio). An indicator needing more sessions than are cached is `None` with a note; RSI and MACD periods come from `TechnicalIndicatorsConfig`. Floats are rounded to 4 decimals. `trend.py::calculate_trend(candles, exchange)` judges the daily and weekly trend from B1's `moving_average` blocks (SMA 50 and 200): `up` for close > SMA 50 > SMA 200 with the SMA 50 rising, `down` the reverse with it falling, else `sideways`; on the SMA 50 alone (`basis: sma_50_only`) when the SMA 200 needs more history, and unjudged (`null`) without an SMA 50. `last_cross` is the latest change of side of the rounded averages (a touch isn't a cross). `weekly_candles(candles, exchange)` builds ISO-week candles from the daily ones, closed weeks only: the newest week counts once its last scheduled session is cached. `levels.py::calculate_levels(candles, exchange, ex_dividend)` builds zones over the last 500 sessions from swing highs and lows (5 sessions each side; not a low on an ex-dividend date), the top 10% of half-ATR volume-profile bins, last closed week's floor pivots and the SMA 50 and 200, merged within half an ATR into zones at most 1.5 ATR wide (at least half an ATR), marked `round` where a round number lies in them. A touch is an episode of sessions whose range enters the zone (or a gap across it); a turn closes back out within 3 sessions and reaches 1 ATR (as of the touch) beyond within 10, before any close through. `strength` is 0–100 (0.55 turns up to 10, 0.20 recency, 0.15 volume share up to 10%, 0.10 other sources up to 3). Per side of the last close it lists the 3 strongest zones with at least 2 turns within 5 ATR, nearest first (a zone holding the last close always, first, at distance 0), else the nearest beyond alone, searching the whole history when the window has none; a close beyond every earlier high (or low) leaves that side empty with a note. `support_signs` lists what points to the first support holding or breaking (trend, SMA 200, down-day volume, RSI divergence, momentum, retests, a recent close below, turns), never summed. Every threshold is a named constant at the top of the module.
- **`fartt/features/`** — calculations over Polars DataFrames and return series: `calculate_technical_indicators.py` computes Bollinger Bands / EMA / MACD / RSI via `talib` for the chart, configured through `technical_indicators_config.py`; `calculate_candle_returns.py` computes the signed percent change per candle; `calculate_trade_returns.py` is a functional long-only backtest over a candle-return series (cost, default 0.05% per leg; slippage, threshold, maximum holding period and stop loss; an optional `predicted_candle_returns` argument backtests a signal known one tick ahead against realised prices).
- **`fartt/visualization/`** — `candlestick_chart.py` (Bollinger/EMA/MACD/RSI overlays via `mplfinance`) and `plot_styles.py::apply_plot_styles` (shared tradingview-style `rcParams`).
- **`fartt/constants.py`** — centralized string labels (column names, indicator labels) and a small colour palette, shared by the features and visualization code to avoid stringly-typed column name drift.

## Team workflow (unity)

This project is built by one developer and Claude in four roles: design -> build -> test -> review. Design is a conversation with the developer (`/unity:design`). Build, test and review each run as their own agent with a **fresh context** (`unity:builder`, `unity:tester`, `unity:reviewer`), started one after the other by `/unity:ship`, or one at a time by `/unity:build`, `/unity:test` and `/unity:review`. Each role is named after the board column it works in. GitHub is the only handoff between roles.

### Board

GitHub Project columns are the workflow state. IDs live in `.claude/pipeline.json` (written by `/unity:init`). Picking an issue with `/unity:design` sets the flow in motion; from then on each role moves the issue to the next column, and `/unity:ship` starts the next agent only when the issue moved on. `/unity:status` shows every issue per column with the next command to run.

| Column | Meaning | Moved there by |
| --- | --- | --- |
| Backlog | Not picked up yet | the developer |
| Design | Design and plan in progress, with the developer | `/unity:design` at start |
| Build | Design approved; implementation and unit tests (TDD), also rework | `/unity:design` once the developer approves the design in conversation; the tester and the reviewer on rejection |
| Test | PR ready, integration testing | the builder when every task is done |
| Review | Tests passed, final code review | the tester on PASS |
| Done | Merged | the board's "Item closed" workflow, when the merge closes the issue |

The developer's approval of the design is the one human gate: `/unity:design` moves an issue to Build only after it, and the builder works only on issues in Build.

### Conventions

- **Branch:** `feature/<issue>-<slug>` (e.g. `feature/42-guest-checkout`).
- **PR body** contains `Closes #<issue>`.
- **Design and plan live in the issue, not in the repository.** The latest `role:design` comment holds both. This overrides any convention that commits specs or plans as files (such as `docs/specs/` and `docs/plans/`), and the file-saving steps of planning skills: post the content as the comment instead.
- **Role comments** start with a hidden marker so the next role can find them: `<!-- role:design v1 -->`, `<!-- role:build -->`, `<!-- role:test -->`, `<!-- role:review -->`. A revised design is a new comment with a higher version; the latest one counts. The design is posted on the issue; build, test and review post on the PR, and each also leaves a one-line pointer on the issue (no marker), so the issue shows the whole flow.
- **Acceptance criteria** are part of the design comment, numbered and testable from the outside:

  ```markdown
  <!-- role:design v1 -->
  ## Design
  ...
  ## Acceptance criteria
  - AC1: A guest can complete checkout without creating an account
  - AC2: An invalid email address shows an inline error and blocks submission
  ```

  Every role refers to criteria by ID: tests are tagged `@AC2`, the test role reports coverage per criterion, review checks that each one is met.

### Testing responsibilities

- **Build** owns unit tests, written test-first.
- **Test** owns the integration tests, and never changes application code or unit tests.

### Integration testing
